# `backend/`

The database schema, the migrations that built it, and the authorization gate that
decides whether a scan is allowed to happen at all. If `scrapers/` is "how we look at a
website," this is "who's allowed to be looked at, and how we remember what we found."

## Why an ORM instead of raw SQL

Week 1's scraper (`scrapers/common/storage.py`) used plain `sqlite3` and hand-written
SQL - fine for one table. This project's full schema has 11 tables with real
relationships between them: a `scan_run` belongs to an `engagement`, a `raw_finding`
belongs to a `scan_run`, a `cve_match` references both a `scan_run` and a
`tech_fingerprint`. Writing and maintaining that by hand in raw SQL strings gets
error-prone fast - a typo in a column name fails silently at runtime instead of loudly
when you write the code.

**SQLAlchemy** (`app/db/models.py`) is an ORM - an object-relational mapper. Instead of:

```sql
INSERT INTO engagements (business_id, status, max_tier_allowed) VALUES (?, ?, ?);
```

you write:

```python
Engagement(business_id=biz.id, status="authorized", max_tier_allowed=3)
```

and SQLAlchemy generates the SQL, tracks the relationships (`engagement.business` gives
you the actual `Business` object, not just an ID you'd have to look up yourself), and -
critically for this project - lets a tool like Alembic compare "what the code says the
schema should be" against "what the database actually has" and generate the difference
automatically.

## Why migrations instead of just editing the database

A **migration** is a small, committed-to-git Python file describing one schema change.
`migrations/versions/507784d1d827_full_schema.py` is our first one - it adds 9 new
tables and 6 new columns to the 2 tables Week 1 already had.

The alternative - everyone just runs `ALTER TABLE` commands by hand on their own copy of
`data/cybersafe.db` - falls apart the moment two people make different changes, or
someone joins the project three weeks in and has no idea what state their database
should be in. Migrations fix this: `alembic upgrade head` brings *any* database,
starting from *any* prior state, to the exact same schema, by replaying the same
recorded steps everyone else replayed.

**This mattered concretely here.** Week 1's scraper had already populated 536 real
businesses before Week 2's full schema existed. We didn't want to lose that data by
recreating the database from scratch. Alembic's `--autogenerate` compared our
SQLAlchemy models against the *live*, already-populated database, and wrote a migration
that only added what was missing - we ran it, and verified all 536 rows were still
there afterward (see the commit history). That's the actual point of migrations: they
let a schema evolve without destroying what's already in it.

### Running migrations

```
cd backend
python -m alembic upgrade head     # apply any migrations you don't have yet
python -m alembic revision --autogenerate -m "describe your change"   # after editing models.py
```

Always review an autogenerated migration before running it - Alembic is very good at
detecting *table and column* changes, less reliable about detecting a plain column
rename (it'll often see that as "drop one column, add a different one," which loses
data if you don't fix it by hand first).

## The schema, briefly

Everything in `app/db/models.py` mirrors `docs/architecture/PLAN.md` Section 4. The
shape worth understanding: `businesses` and `engagements` are the only tables that exist
before any scan happens (Week 1 populates them). Everything else -
`scan_runs`/`raw_findings`/`tech_fingerprints`/`http_headers_findings`/`tls_findings`/
`cve_matches`/`anomalies`/`reports` - only gets rows once a scan actually runs against
an *authorized* engagement, which is exactly what the gate below enforces.

`demo_showcase_runs` is deliberately separate from all of that - it's the *only* table
the future public website is allowed to query, holding anonymized/synthetic examples,
fully decoupled from real engagement data. A bug in the public site's code literally
cannot leak a real business's findings, because the public site's code was never given
a way to reach the tables that hold them.

## The authorization gate - the most important file in this folder

`app/auth/gate.py`'s `assert_engagement_authorized(db, engagement_id, requested_tier,
target_url)` is called before any scraper module runs. It checks, in order:

1. Does this engagement exist?
2. Is its `status` literally `"authorized"` (not `"draft"`, not `"pending_signature"`,
   not `"revoked"`)?
3. If it has an expiration date, has that date already passed?
4. Is the requested tier within what was actually authorized (`max_tier_allowed`)?
5. Is the target URL's host actually in the list of hosts this engagement covers
   (`in_scope_hosts`)?

If *any* of those fail, it raises `ScanNotAuthorized` and returns nothing - the caller
never gets far enough to invoke a scraper. This is a **fail-closed** design: the default
behavior when anything is wrong, missing, or ambiguous is "refuse," not "proceed with a
warning." That's a deliberate security posture, not just defensive coding style - a
scanning tool that fails *open* (scans by default unless something explicitly blocks it)
is one config bug away from scanning a business that never agreed to it.

### Why the tests matter more than the function

`tests/test_gate.py` has 8 tests. Seven of them prove the gate *blocks* the wrong
things (draft status, expired authorization, tier too high, host not in scope, an
engagement that doesn't even exist). But the eighth,
`test_authorized_in_scope_engagement_reaches_the_scraper`, proves the opposite - that a
*correctly* authorized request actually gets through.

That second kind of test is easy to skip and easy to regret skipping. A gate function
that's buggy in the "blocks everything, including things it shouldn't" direction would
still pass all seven of the first tests - it would just be useless, and nobody would
notice until a real, legitimately-authorized scan mysteriously failed. Testing both
directions is how you know the gate is *correct*, not just *strict*.

Each test uses a fake scraper function that raises `ScraperCalledError` if it's ever
actually invoked:

```python
def fake_scraper_call(target_url: str) -> None:
    raise ScraperCalledError(f"a scraper module was called against {target_url!r}")
```

This turns "the gate silently let something through it shouldn't have" from a bug you
might never notice into a loud, immediate test failure - which is a useful pattern
worth reusing anywhere else in this project where "X must never happen" is a real
requirement, not just a nice-to-have.

### Running the tests

```
python -m pytest backend/tests/ -v
```
